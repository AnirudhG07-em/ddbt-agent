# LGA (Layered Governance Architecture) — a four-layer agent-governance stack whose core is an L2 LLM "intent judge" gating every tool call

- **Source:** "Governance Architecture for Autonomous Agent Systems: Threats, Framework, and Engineering Practice", Yuxu Ge (University of York), arXiv:2603.07191v1 (2026). https://arxiv.org/abs/2603.07191
  - NOTE: the assignment referenced "Ge et al., 2026, arXiv:2603.07191, four-layer governance, intent judge at L2" — that ID and description are **confirmed**. The single listed author is Yuxu Ge (not "et al."); "LGA / Layered Governance" is our shorthand, the paper's own title is the one above.
- **Category:** layered runtime governance — sandbox isolation + LLM intent-verification judge + zero-trust inter-agent auth + immutable audit (defense-in-depth, not pure IFC)

## Pipeline (stage by stage)

LGA wraps an agent in four cooperating layers. The defining mechanism is **L2 intent verification**: an independent LLM judge that compares the *trusted task* to the *proposed tool call* and emits ALLOW/BLOCK before execution.

End-to-end, when the agent proposes a tool call `a` under task `T`:

1. **L1 — Execution Sandbox (deterministic, always-on).** All agent code runs inside OS-level isolation: Linux containers / seccomp filtering / read-only mounts / namespace isolation (`unshare` in the prototype). This is the always-on containment boundary regardless of what the judge decides. ~1 ms overhead. The paper explicitly positions L1 as the layer you trust when L2 fails.

2. **L2 — Intent Verification (LLM judge, on the hot path).** A judge function `𝒥` receives a structured prompt (Listing 1) containing:
   - the **original task description `T`** (trusted, from user/system), and
   - the **proposed tool invocation `a`** rendered as a raw function-call string (untrusted — generated by the agent).
   It outputs **ALLOW** or **BLOCK** based on semantic consistency between `T` and `a`. In the *standard configuration the judge does NOT receive external documents or raw tool outputs* — only `T` and the call string.
   - **Two-stage cascade (recommended deployment):** stage 1 = a high-recall cheap local model (Qwen3.5-9B) flags suspicious calls; stage 2 = a precision model (GPT-4o-mini cloud, or Qwen2.5-14B local) refines. Cascading drops FPR from 34.1% → 1.9% while keeping ~91.9% interception.
   - On BLOCK → escalate to human review (the authors recommend human triage of L2 escalations rather than treating the judge as a fully autonomous gate).

3. **L3 — Zero-Trust Inter-Agent Protocol (deterministic).** Minimum-privilege capability tokens with strict TTL and scope; inter-agent messages authenticated with HMAC-SHA256 + JSON-Schema validation. < 0.02 ms. Stops a compromised/poisoned agent from over-reaching against peers.

4. **L4 — Immutable Audit Log (deterministic).** Append-only, durable (fsync) record of every invocation: tool, arguments, return values, timestamp, agent identity. 4–12 ms per call. Designed so a compromised agent cannot delete its tracks (the gap they found in OpenClaw).

**Cost split:** in the 100-sample end-to-end run, L2 dominates latency (~2.8–3.0 s P50 for the cascade; ~980 ms P50 reported for the full pipeline on the lighter config) while L1+L3+L4 add only ~18 ms combined.

## Key mechanisms

- **Task-vs-action semantic consistency as the gate (L2).** The judge does not ask "is this action intrinsically bad"; it asks "does this tool call serve the stated task `T`?" — i.e. an intent/goal-fidelity check, the same axis ddbt calls Axis 1.
- **Two-stage judge cascade** (cheap high-recall → expensive high-precision) to get acceptable FPR at acceptable cost; a single strong model (Qwen2.5-14B) hits 98% IR but 10–20% FPR, which the cascade fixes.
- **Constrained judge input by design.** Judge sees only trusted `T` + the action *call string*, deliberately NOT the external documents or tool outputs — this is their (partial) injection mitigation.
- **Defense-in-depth with L1 as the trust anchor.** Sandbox (L1) is the always-on floor; the judge (L2) is an additional, fallible filter, not the sole boundary.
- **Tamper-evident accountability (L4) + least-privilege capability tokens (L3).**

## Strengths / what's genuinely good

- **Honest, well-bounded evaluation.** Bilingual benchmark of 1,081 tool-call samples — TC1 prompt injection (141 direct + 180 indirect), TC2 RAG poisoning (136), TC3 malicious skill plugins (120), plus 504 benign + 40 hard-negative plugin samples. Cascade: **91.9–92.6% interception at 1.9–6.7% FPR** on TC1/TC2; 99–100% IR generalizing to the external InjecAgent benchmark.
- **Explicit, layered threat model** mapped to layers, and a concrete case study (OpenClaw) naming four real governance gaps: G1 soft LLM-semantic constraint enforcement, G2 self-declared plugin permissions, G3 no intra-directory permission partitioning, G4 mutable audit logs.
- **Realistic latency accounting** that names L2 as the cost center and keeps the deterministic layers near-free.
- **L4 immutability and L3 capability tokens are clean, deterministic, hard-to-argue-with wins** independent of the judge's quality.

## Limitations / failure modes

- **The L2 judge is itself injectable / evadable — and the paper admits it.** The threat model is explicitly scoped to "a black-box, **non-adaptive** adversary … with no knowledge of the deployed judge model … Adaptive attacks—where the adversary iteratively optimizes inputs against a known judge—are outside the scope of this work." A hand-crafted 30-sample adversarial probe (double negation, task disguise, authority injection) drops interception to **50–63%**. They concede "dedicated adversarial training or ensemble defenses are needed for deployment against sophisticated threat actors."
  - **This is the exact flaw ddbt's design critiques.** Even though LGA's judge nominally sees only `T` + the action string (not raw tool output), the *action string itself is attacker-influenced* (an indirect injection steers the agent into crafting a call whose arguments smuggle the adversary's framing), and the judge's verdict is produced by an LLM reading that attacker-influenced text. The judge is a soft, promptable decision-maker, so it inherits promptability. LGA's mitigation (restrict the judge's inputs) *reduces* but does not *eliminate* injectability — and they don't claim it does.
- **TC3 (malicious plugins) is materially weaker:** ~75–94% IR among balanced judges — intent-consistency reasoning is a poor fit for supply-chain/plugin threats.
- **High L2 latency** (~2.8–3 s P50 for the cascade) on the hot path.
- **Cost/FPR tension:** strong single judge = high FPR; cheap judge = high FPR too; only the cascade balances, adding a second model call.
- **Cloud second stage** (GPT-4o-mini) sends the task + action string off-box — a data-egress/trust concern for sensitive workspaces.
- **English results are machine-translated** from a Chinese-original benchmark; some bias possible.

## Best pieces to steal for ddbt

- **L1-as-trust-anchor is the structural lesson for our injectable-judge tradeoff.** LGA's own conclusion — *the LLM judge cannot be the sole gatekeeper; keep an always-on deterministic containment floor and triage judge escalations to humans* — directly validates ddbt's v3 instinct. Concretely: pair ddbt's step-judge with a non-bypassable deterministic boundary (workspace jail / staging overlay / no-network-by-default), so that even a fully-injected judge cannot cause irreversible harm. Treat the judge as a *filter that raises suspicion*, not the last line.
- **Two-stage judge cascade maps cleanly onto our suspicion ratchet.** Run the cheap local model on every call (stage 1, high-recall). Only escalate to a stronger/second model when stage 1 flags *or* when session suspicion is ELEVATED/LOCKED. This gives ddbt LGA's FPR win (34%→2%) while keeping per-call cost low — and it naturally ties the second, expensive judge to the ratchet we already have.
- **Constrain the judge's diet — but go further than LGA.** LGA already withholds raw tool output from its judge. ddbt's known tradeoff is precisely that *our* judge reads untrusted tool-output bytes. Borrow LGA's "judge sees trusted task + structured action descriptor only" as the default, and reserve content-reading by the judge for an explicitly-quarantined, clearly-delimited, suspicion-gated path. This is a direct, concrete reduction of our injectable-decider surface and is essentially the v3 "blind judge" idea with LGA empirical backing.
- **Adopt L4 immutability hardening for our audit log.** ddbt already has an append-only audit log; LGA's G4 finding (compromised agents delete audit records) argues for fsync-durable, tamper-evident writes (e.g. hash-chained entries) stored outside the workspace — which dovetails with ddbt's existing "store quarantine/state OUTSIDE the workspace" invariant.
- **Build an adaptive-attack red-team set, because LGA didn't.** Their headline 92% collapses to 50–63% under 30 hand-crafted adaptive probes. ddbt should bake an adaptive-evasion suite (double negation, task disguise, authority injection, tool-output framing) into `bench/` as a standing regression, and use it to justify *why* the deterministic floor and the suspicion ratchet exist.
- **Steal L3 capability tokens for any multi-agent / MCP fan-out** (TTL- and scope-bounded, HMAC-authenticated) to bound blast radius if a sub-agent or MCP server is poisoned — complements Boundary 0's integrity check with runtime least-privilege.
